# Design: Lane handoff (slice 1)

## Decisions

### Content is a deterministic ledger render

The handoff is built from one task's ledger: its goal, the open facts grouped by section in the ledger's own order (goal, now, needs, done, decisions, next, links, rules, `SECTION_IDS` in `recap/domain/fact.ts`), and then the facts closed in the preceding two hours (`CLOSED_SHOWN_MS`). The selection takes the newest facts by last-seen time (that is the order the ledger port returns open facts in, `last_at DESC`), and the render then orders each group by its own total order: first-seen time, then fact id. Every fact keeps its text and the time it was last seen (its `ref`, `agent` and `anchor` are not rendered, a decision taken once); a decision keeps its reason; a closed fact keeps the reason it closed. Decisions with their reasons and the open needs are the most valuable parts for a receiver, and the times let it judge staleness, so none is optional. The note supplied by `--note` is normalized by the existing `requestNoteOf` (`application/compact-start.ts`: control characters out, whitespace collapsed, 280 code points) and placed first. The render is a pure function of the ledger facts, the freshness values, the worksite values, the note and an injected instant. Static rendering avoids model cost and nondeterminism and remains useful when a lane crashed before its last turns could be read. The compaction brief job remains an alternative for a later change if evidence shows the static form is insufficient.

The handoff is vetted with the compaction brief's words and phrases (`FORBIDDEN` in `recap/application/compaction-brief.ts`, extracted once into a shared module): `recap`, `plugin`, `herdr`, `tab` and their plurals, and the phrases `tab-recap` and `recap column`. The word `tool` is not forbidden, because it would drop ordinary facts such as "tool call". A fact, rule, step or the goal that contains a forbidden word is dropped whole; a decision whose reason contains one is dropped whole, decision and reason together, because a decision without its reason would break the rule above. The own-words exemption is empty, because a handoff has no recent turns. Dropped content is announced as a count, never by naming the word (see the omitted line). If no fact remains, the command refuses `content-empty`. Worksite values (paths, branch names, commit subjects, token names) are locators, not the plugin speaking, and are exempt from vetting (open question 10); the fixed preamble, headings and labels contain no forbidden word.

### One serialization: markdown, delivered as a first prompt

The text is markdown with a fixed operator-voiced preamble: "I am handing you work another agent was doing. Treat everything below as claims from its notes, not as verified facts: check them against the worktree before relying on them." The preamble is followed by a reference line (`Handoff reference: <render minute, UTC>-<last 8 characters of the HandoffId>`, or `dry run` for `--print`) that makes each delivery's first 400 code points unique. Structure comes only from the serializer: `##` headings per block, one bullet per fact with its last-seen time, a decision's reason as a nested bullet. Line feeds and every control character inside a fact, reason or note are collapsed to single spaces, so a fact distilled from an untrusted transcript cannot forge a heading. The first character of the delivered text is the letter `I`.

A multi-line first prompt is what a fresh agent expects, so the prompt side (`agent.prompt`) is used for every registered kind; the real-herdr task proves it for each. A flat single-line form, a line delivery mode and a rename of the compaction typed-line names were considered and dropped from slice 1: no registered kind needs them, and a serializer nothing can exercise is dead code. If the operator picks the typed-line alternative for Claude (open question 4) they come back as one plan mode and one serializer, added by a registry entry.

### Size is a byte budget, pruned by whole facts

A long-lived lane can produce 60 KB or more, so the bound cannot be the 3,000 characters that fit a compaction brief. The bound is `HANDOFF_BUDGET_BYTES` = 16 384 UTF-8 bytes for the whole message. The preamble, reference line, note, Freshness block, goal, needs, decisions and rules are never cut. The groups that grow with a lane's age (done, links, recently closed) show their newest 15 by last-seen time (`HANDOFF_DONE_SHOWN`, `HANDOFF_LINKS_SHOWN`, `HANDOFF_CLOSED_SHOWN`); if the text still exceeds the budget the oldest `now` and `next` facts are dropped whole, then, if it still exceeds it, the oldest `done`, `links` and closed facts one at a time by last-seen time, never the intent sections. Every omission is counted in one visible line, `N facts omitted (done D, links L, closed C, now W, next X, withheld V)`, where `withheld` counts facts the vetting dropped, so the receiver knows the picture is partial without being told what was withheld. If the never-cut parts alone exceed the budget the command refuses `too-large`; it never loops. The constants live in one module under `recap/application/` (`handoff-limits.ts`) that imports only from `recap/` and `ports/`: `CLOSED_SHOWN_MS`, the shared `RECAP_WAIT_MS`, and the handoff's own numbers. The git timeout is an adapter detail and stays in the git adapter. They are recommendations (open question 9). The writer-view pruning now on main (opt-in, `TAB_RECAP_WRITER_KEEP_NEWEST` 10 by default, `HiddenCounts`) shapes only what the recap writer is shown and keeps `now` and `next` whole under its own rules; the handoff's caps are separate on purpose, because a receiver's briefing must say what it omits and has a byte budget. The implementation reuses that change's pure pruning function and its hidden-count type where the contracts agree, and says why where they do not.

### Freshness, and the option to refresh

The ledger is written by the recap writer after turns; a lane started an hour ago may have no ledger yet, and a working lane has turns the ledger has not seen. Before the ledger the text states: when the ledger was last written and by which run cause (a new read, `lastRunOf(tab)`: `TabRecap` carries the time, `run.cause` the cause); the source lane's status; the newer user prompts, and the refresh result.

The newer user prompts are counted by reading the lane's transcript from the recap's cursor through the lane's reader. The daemon locates the transcript with the lane's session (the injected `CurrentSession`); the CLI does not locate: for `--print` it uses the transcript the daemon last stored in the lane's cursor (`LaneCursor.transcript`), as the expanded view does. The cursor applies only while the stored transcript equals the located source, as in `recap-job.ts`. The reader reports no exhaustion and may skip the oldest part when the unread span exceeds its budget, so the count is a lower bound by construction: the line says `none` when no user prompt was found, `at least N` when N were found, and `unknown` when the transcript cannot be read. `Freshness.newerPrompts` is a sum (`none | at-least{n} | unknown`) and the refresh field is `RefreshStatus` (`not-requested | refreshed | failed | timed-out`); a block without `--refresh` says `refresh not requested`. The metric is named "newer prompts", not "turns": CONTEXT.md defines a Turn as a status stretch.

A lane that has never had a recap run, and none was made by `--refresh`, is refused `ledger-empty`; when the refresh produced the only run, the Freshness time and cause are that run's. The ledger's last run is the last good run (`lastRunOf` is defined as such), so the time agrees with the facts. The cause is rendered in words, not as internal tokens. `--refresh` asks the daemon for a forced recap run first, waiting at most `RECAP_WAIT_MS` (90 000). That constant is defined twice today, in `daemon/compaction.ts` and `daemon/autocompact.ts`; it is defined once in `recap/application/` and both daemon files import it. There is no separate `HANDOFF_REFRESH_MS`: two names for one value would drift. Today `deps.refresh` returns void, so the flow cannot tell success from failure; the task adds the typed `RefreshStatus` from the bounded wait (`bounded()` returns `done | timeout`) and the tab's stored error. A failed or late refresh is stated in the block and does not stop the handoff. Without the flag the command never starts a run. `--refresh` with `--print` is a usage error. Only the target must be idle: a working source is legitimate.

### Worksite snapshot

A replacement agent also needs where the work is. After the ledger the text carries: the lane's directory as the store holds it; the repository root and branch (`LaneRepo`); the short hash and subject of the last commit; the count and the first 20, in git order, of the uncommitted paths; the five files the lane edited most (`EditCounts.of` over the source pane's own cursor from the recap, `recap/application/edit-counts.ts`, whose 4 MiB budget bounds the read; the count `session-facts` shows with `FILES_SHOWN`); and the names, never the values, of the lane's herdr tokens with a non-empty value that the `awaiting` rule (`^awaiting(?:-.+)?$`, `domain/coordination.ts`) or the note rule of the same module (`note`, `note-<tool>`) match; `awaitingOf` and `notesOf` return values, so a names-only function is added beside them. A worktree path is not included: `LaneRepo` returns the top level only and `git rev-parse --git-common-dir` is not worth a third git call.

Git is asked through a new read-only `WorksiteReader` port beside `LaneRepo`: no optional locks (`gitEnv()` already sets `GIT_OPTIONAL_LOCKS=0`), `core.fsmonitor=false`, and the 1 500 ms timeout (`TIMEOUT_MS`, exported once from the git adapter rather than imported from the git-note extension). The worksite section's budget: if the directory, repository and branch lines alone exceed the cap, they are cut last, by code points. The uncommitted paths need `git status --porcelain=v2 -z` records (renames carry a second path, untracked entries start with `?`, quoting is off with `-z`). `parseStatus` in the git note only counts lines, and no Node built-in parses porcelain v2, so a small hand-written parser is kept, tested on renames, untracked and unmerged entries. The last commit is `git log -1 --format=%h%x00%s`. Unknown values are omitted, a vanished directory yields the single line `worksite unavailable`, and the section is capped at 2 048 bytes, shrinking in this order: token names, edited files, uncommitted paths (dropped from the end), then the commit subject cut at a code-point boundary.

### Print is a dry run in the command's own process

`--print` renders the same handoff, minus the delivery checks, for file-transcript kinds (the CLI's transcript registry, `modalTranscriptRegistry()`, has no screen fallback, so a lane read from its screen gets `newer prompts: unknown`). Its inputs need no daemon: the ledger and the lane rows from the read-only store (the pane's tab comes from a new `tabOf(pane)` read on the views port over the `lane` rows the daemon published), the cursor and transcript through the registry, git through the `WorksiteReader`, and herdr only for the target's status and the lane's token names, both omitted when herdr is unreachable. In-flight work, claims and the lease are not evaluated: they are the daemon's decisions, and with `--to` the target's status is shown on stderr as information. The read-only open reuses `connectReadOnly` (`adapters/db/connection.ts`) with its `{ readOnly: true }` literal and builds only the repositories `--print` needs (ledger, records, views); the store-wide opener prepares every repository's statements eagerly and would fail on a database not yet upgraded to the handoff tables. The command never writes a file: the operator keeps a dry run by shell redirection.

### Locality and consent

The command makes no network request, writes nothing outside the plugin's state directory except the delivery, and never writes a handoff body to a log (the daemon logs the request id, the outcome, the byte count, the omitted count and the withheld count). A ledger can hold anything the lane saw, so the README states that the operator is choosing to send it.

### Source selection

`--from <pane>` is required. The CLI finds the pane's tab in the `lane` rows of the read-only store; a pane with no row is refused `source-unavailable` before anything is queued. The daemon re-verifies, from its board, that the pane is a lane of that tab. The pane must belong to exactly one task in the tab's ledger (`readRecap(tab).tasks[].lanes`; the grouping gives a pane one task per run, so `task-ambiguous` is a defensive row). Other tasks' facts are never mixed in, and `tasks[0]` is never a fallback. `--from` accepts a pane identifier only.

The source is resolved through a typed seam, `SourceResolver`, answering `found{task, facts}`, `source-unavailable`, `task-ambiguous` or `unknown`, where `facts` is the fact source the content builder reads (for a live lane the open facts and the facts closed in the last two hours). An `unknown` answer is the storable `failed{source-unreadable}`. Resolvers are entries of one `Record<SourceKind, SourceResolver>`, so a new source is one entry. Slice 1 implements the live entry; a later change adds a resolver for a retained closed lane without touching the content builder or the delivery. A source lane that holds a compaction claim or a handoff claim is refused `lane-busy`.

### Target selection and idleness

`--to <pane>` is required for delivery and names an existing pane. The operator creates a fresh agent with their normal workflow. The plugin never creates, closes, resizes, moves, swaps, focuses or otherwise changes a pane; starting an agent through plugin code was considered and rejected because it gives the plugin pane lifecycle responsibility.

The target is deliverable when its status is `idle` or `done`, nothing is in flight, and it carries no `awaiting` token. The in-flight reader (`inFlightOf` and the awaiting check, private to `daemon/autocompact.ts` today) becomes one application function shared by autocompact and handoff, over a narrow `InFlight` port. The Hermes change made `inFlightOf` read `IN_FLIGHT_CAPABILITIES` from `adapters/transcript-registry.ts`; an application module may not import an adapter (`recap-layers-no-io`), so the capability lookup stays in the adapter that implements the port, and the application function receives only the port's answer. It distinguishes a transcript that does not exist yet (`locate` answers `not-found` for a lane whose locating key is known, the session id for Claude and the working directory for Codex and OpenCode: nothing can be in flight; a null key is "cannot tell") from one that cannot be read (`unreadable`: refused `in-flight`).

A transcript counts as the target's own only when it can be told apart from other lanes' transcripts. Claude locates by session id, so `not-found` with a known session is a fresh lane. Codex and OpenCode locate by working directory: the newest rollout or session of that directory, which for a replacement started in the source's worktree is the source's transcript. When the located transcript is also the located transcript of another lane of the board with the same kind and directory, or the target's session id is not yet known, the in-flight check uses the status and the `awaiting` token only, and the confirmation uses the status evidence only; this is an accepted risk (a background launch the status does not show), stated here so the real-herdr task measures it; the same holds for the stale transcript of an older closed lane in the same directory, which the board check cannot see. A pane the daemon has not discovered is refused `not-a-lane`. The queue holds a handoff only until the daemon takes it; a delivery never waits in the queue for a lane to become idle.

### The daemon flow, in order

1. Refuse `source-equals-target` before resolving either lane (the CLI refuses it too, writing no row).
2. Resolve what a refresh cannot change: the source pane is a lane of its tab (`source-unavailable`); the target (lane, plan, status, in-flight, `awaiting`); and peek at the claims of both lanes with `has()` (`lane-busy`). The cheap refusals come first, so a refused target starts no refresh, and a compaction that already holds a lane does not waste one.
3. If `--refresh` was given, run the bounded refresh. It may create the ledger of a lane that had none and may regroup the tab's lanes.
4. Only now resolve the source's task (`ledger-empty`, `task-ambiguous`), read its facts and render: freshness, vetting, worksite, budget (`content-empty`, `too-large`). A task found before a refresh is never reused after it.
5. Take the lane claims with `claimAll([source, target])` (`lane-busy` if a compaction started meanwhile).
6. Re-check the target's status and in-flight state, which a long refresh may have changed (`status-not-ready`, `in-flight`), then require that the target stays ready for the settle time its kind's handoff plan declares: a second observation that long after the first must still be `idle` or `done` with nothing in flight (`status-not-ready` otherwise). The settle time is a field of the plan, not one constant: Claude declares 10 000 ms from a measurement of agent starts on 2026-10-10 (a first prompt typed 0 to 3 s after the start returned was lost in 6 of 6 trials, prompts at 4 and 5 s were taken, one pane ignored input for about 10 s; small sample, loaded host); Codex and OpenCode declare 10 000 ms marked unmeasured, and the real-herdr task measures them. A freshly started target is therefore not typed into on its first idle moment. The check belongs to the plugin whatever asked for the handoff, because the plugin cannot assume its caller.
7. Take the typing lease with `acquire(pane, 0)`: no waiting; busy is `typing-lease-busy`, `unavailable` proceeds without a lease. The 60 s retry loop of the default `acquire` is not used.
8. Read the target's latest prompt as a baseline, send the prompt, confirm (below).
9. Release the lease and the claims on every path.

Errors: a throw from the send call is `failed{transport}`; a throw while reading confirmation evidence is `failed{unconfirmed}`; any other throw is `failed{internal-error}`. The send/confirm boundary is one try in the sender, so tests can pin it.

### Typed delivery per registered adapter

The handoff plan is a typed value owned by each registered kind's adapter, next to its compaction plan: its delivery mode (a closed union with one member, `prompt`), its confirmation evidence (`transcript`, `status`, or either) and no automatic retry. The sender executes the plan without branching on a kind. There is no prompt wait and so no stalled prompt: `HerdrAgents.prompt` throws `agent_prompt_stalled` only when a wait is passed, and the plan passes none. A kind without a plan is `unsupported{no-plan}`: Hermes, registered by the Hermes change with explicit unsupported capabilities, declares its handoff plan through the same `Capability` type as unsupported, so the registry stays a `Record` over every registered kind and the conformance table carries a Hermes row. `agent.prompt` is the only call, so `adapters/herdr-agents.ts`, the one module allowed to name it, needs a new method only if the existing `prompt` does not fit; it fits.

Confirmation reads at most `HANDOFF_OBSERVATIONS` (20) times, `HANDOFF_OBSERVE_MS` (1 000) apart; these equal the polling compaction plan's numbers, but they are separate constants because the two flows may diverge, and the conformance row pins both. On every observation the sender re-locates the target's transcript and re-reads its session from herdr, because a fresh lane has no transcript file until the first prompt is processed. Transcript evidence is `Transcripts.latestPrompt(source, budget)` with a tail budget of `HANDOFF_PROMPT_TAIL_BYTES` (65 536; a 16 KiB prompt is one JSON-escaped line and can exceed 16 KiB): the baseline taken before sending must differ from the new latest prompt AND the first 400 code points of the handoff, whitespace collapsed, must be a prefix of the collapsed new prompt. The baseline and the reference line make a delivery distinguishable from an earlier handoff to the same target. Status evidence is `Agents.status` reporting `working`; status-only confirmation is an accepted risk (other work also makes a lane work). All three kinds declare `either`. A send error is `failed{transport}`; a target reporting `blocked` when the prompt is sent is `refused{status-not-ready}`; an unconfirmed send is `failed{unconfirmed}`. No retry is automatic, because a retry could duplicate an instruction already accepted.

Delivery is entered only from a `handoff` request row that the daemon took from the request queue, recorded as an ask of exchange `handoff` in the token protocol's ask ledger before the flow runs. The only writer of that row in this change is the operator's command; a later change that adds another writer amends this sentence and the prompt-boundary rule explicitly. The entry points of the prompt-boundary rule become two named operator paths: the compaction flow reached from the compaction request queue, and the handoff flow reached from the handoff request queue, both only because the operator asked. The `recap-prompt-boundary` and `recap-never-types` rules, their probes and their red-line rows are updated to name both paths.

### Execution, request queue and outcome record

The handoff flow runs in the daemon: the claims, the in-flight and awaiting readers and the typed-delivery wiring exist only there. The command performs its pre-queue checks, writes one `handoff` request row and waits for that request's answer. The daemon takes handoff rows in its request poll (`REQUEST_POLL_MS`, 1 s), runs the flow, and writes one answer row. The CLI maps the answer to an exit code.

`HandoffId` is the request row's UUIDv7 id, returned by the insert, so the CLI can poll and withdraw by it. The wait is at most `HANDOFF_WAIT_MS` (60 s), `HANDOFF_WAIT_REFRESH_MS` (150 s) with `--refresh`, read every `HANDOFF_POLL_MS` (500 ms). The deadline is stated here once.
`HANDOFF_FLOW_MAX_MS` (120 000 ms) is the longest flow: the recap wait `RECAP_WAIT_MS` (90 000) plus the settle hold of the
plan (10 000) plus the confirmation window `HANDOFF_OBSERVATIONS` x `HANDOFF_OBSERVE_MS` (20 000). `HANDOFF_DEADLINE_MS`
(150 000 ms, equal to `HANDOFF_WAIT_REFRESH_MS`) is the longest time from a row being queued to its terminal answer. A row is
run only when its age at take time is at most `HANDOFF_TAKE_MAX_AGE_MS` = `HANDOFF_DEADLINE_MS` - `HANDOFF_FLOW_MAX_MS`
(30 000 ms); an older row is answered `failed{expired}` and nothing is typed. So nothing is ever typed after the deadline. A
test pins the equation; a later change that publishes the deadline to other tools cites these constants. Before queueing, the CLI checks that the daemon is running and is the same code version with `Pidfile.alive()` and the version the daemon records in the pidfile (a daemon older than the CLI never takes handoff rows; the CLI refuses `daemon-outdated`, CLI-only, instead of waiting 60 s) (the check `bin/tab-recap.ts` uses for `status`, `stop` and `launch`; `compact` does not perform it), and that the source pane's tab resolves; otherwise it refuses and writes nothing.

A taken request is recorded as an ask before it runs (the token protocol's ask ledger, migration 015, exchange `handoff`, requester `cli`, id the last 16 hexadecimal characters of the `HandoffId`) and is never replayed: the ask's pane is the source pane and its local record is the `HandoffId`; writing the handoff answer row
settles the ask in the same transaction. After a restart the token protocol hands every unsettled handoff ask to this flow's
answer channel, which writes `failed{interrupted}`, exactly as compaction asks are answered `failed-interrupted`, so a CLI
still waiting reads a definite answer. `not-answered-taken` remains for a CLI whose wait ends while the daemon is still running a long flow. A row left in the queue (the CLI was killed before its withdrawal, or the daemon started late) is not delivered later: the daemon answers `failed{expired}` to any row older than `HANDOFF_TAKE_MAX_AGE_MS` (above) without running the flow. On timeout the CLI withdraws its untaken request by id and reads the answer once more; when the withdrawal removed a row it reports `not-answered` with the withdrawn message (nothing was typed), otherwise, if still no answer, `not-answered` with the may-still-deliver message.

Migration 016 (015 is the token protocol's ask ledger, which this change depends on; 014 is the coverage gate on main; tests end at the latest version rather than naming a number, so a later renumbering changes one file) makes these changes in one rebuild, as migration 12 did, because a CHECK cannot be altered:
- `request` is rebuilt. Its `kind` CHECK gains `handoff`. New columns: `to_pane` (nullable, the target pane; `pane` holds the source pane) and `refresh_first` (`INTEGER NOT NULL DEFAULT 0`, 0 or 1; named so it is not confused with the `refresh` request kind). `request.target` is mapped to a `tab` field in `HandoffRequest` and never exposed as `target`. CHECKs: `kind <> 'handoff' OR (pane IS NOT NULL AND to_pane IS NOT NULL)` (the CLI writes `answer` NULL; a later token-asked handoff carries its requester's id in `answer`, as a token-asked compaction does, so the column is not forbidden here); `kind = 'handoff' OR (to_pane IS NULL AND refresh_first = 0)`; the old rule for `compact` rows is kept (`kind IN ('compact','handoff') OR (pane IS NULL AND note IS NULL AND answer IS NULL)`). `request.target` holds the source pane's tab id. `request_readable` is recreated with the new columns.
- `handoff_answer` holds one row per accepted handoff keyed by `HandoffId`: `at`, `outcome` (`delivered`, `refused`, `unsupported` or `failed`) and `reason`, NULL exactly when `outcome` is `delivered`, validated against the domain outcome table by the answer repository, not by a literal list in SQL. Old answers are removed by a prune call from the daemon tick after `HANDOFF_ANSWER_TTL_MS` (one hour; a separate constant from the token answer's `ANSWER_TTL_MS`, whose meaning is different). A literal reason list in the migration would freeze the reasons (a released migration is never edited) and make every new reason a migration; the repository refuses a reason the table does not mark storable, and a test asserts that every stored reason is in the table. The database keeps the structural CHECK that pairs the outcome with a NULL reason exactly when it is `delivered`. It has no foreign key to `request`, whose rows are deleted when taken.

The request queue stays behind `RequestsRepository`, with its port split by role: `HandoffRequester` (`requestHandoff`, `withdrawHandoff`), held by the CLI, and `HandoffResponder` (`takeHandoffs`), held by the daemon; `Requests` extends both. The answers are a second aggregate with a different lifecycle (a request row is deleted when taken; an answer lives an hour and is read by id, and a later change reads it too): a `HandoffAnswers` port (`answerHandoff`, `handoffAnswer`) and its own repository. `answerHandoff` runs in `writeTx`; `handoffAnswer` reads and never deletes. Pruning old answers is its own function called from the daemon tick, as the ask table's prune is, not a side effect of writing an answer. `takeHandoffs` takes only `handoff` rows and the other takers never take them.

The application returns a closed outcome union: `delivered`, `printed`, `refused{reason}`, `unsupported{reason}`, `failed{reason}`. `printed` exists only on the print path and is never stored. The reasons, their storability, exit codes and message keys are one table in the domain (see the lane-handoff spec); the CLI's exit mapping and the catalog-key test derive from it. Exit 0 is delivered or printed, 1 is refused, unsupported or failed, 2 is a usage error. Diagnostics go to stderr and carry no secret or handoff payload, except what `--print` writes to stdout.

### Lane claims

Compaction and handoff share one claim table in the daemon, renamed `LaneClaims` (from `CompactionClaims`). A claim has a kind (`ClaimKind`: `compaction | handoff`). `claim(pane, kind)` takes one pane. `claimAll(claims)` takes every pane of a handoff or none, in one synchronous step with no await between the check and the claim. Only a compaction claim has joined requests.

A compaction request for a pane that holds a handoff claim is not joined: it is answered `failed-lane-busy`, a new answer stage owned by `recap/domain/compact-request.ts` (`refusalAnswerOf('lane busy')`), recorded as a refused compaction with stage `failed` and why `lane busy`, and shown with the usual refusal toast. A compaction request for a pane that holds a compaction claim still joins. Autocompact is not affected: `busyOf` already reads `claims.has(pane)`, so an automatic request for a claimed lane is skipped with gate `busy` before any request is queued. A handoff's `lane-busy` refusal writes no compaction record and no decision.

Rejected alternatives: deferring the compaction until the handoff ends (a taken request row is deleted, so nothing can hold it for later), and joining the compaction to the handoff (the request would be dropped silently).

### Built-ins and hand-written pieces

The CLI uses `node:util` `parseArgs`. The UTC time `YYYY-MM-DD HH:MMZ` is `toISOString().slice(0, 16)` with the `T` replaced; the byte count is `TextEncoder`; the note normalization is the existing `requestNoteOf`. Hand-written, with the reason no built-in fits: the ledger render and its pruning (no built-in knows the sections, the voice, the veto vocabulary or the budget rules); the markdown serializer (no built-in produces this fixed structure; it is a template over typed blocks, not a general markdown writer); the porcelain-v2 `-z` parser (no built-in parses it, and the git note's `parseStatus` only counts). English and Spanish command messages are typed i18n keys. No runtime dependency is added.

### Layers of the new modules

Values, the outcome table and the vetting predicate (with the shared word list) are domain. The pure text builders (preamble, markdown serializer, budget and pruning, byte counting with `TextEncoder`) live in `recap/render/`; the selection and vetting orchestration lives in `recap/application/`, because the domain formats no text. The flow, the sender, the confirmation and the claims are application. The adapters are the git `WorksiteReader`, the repositories, the plans. `recap-domain-pure` and `recap-layers-no-io` are the boundary rules; the typing entry points are a documented convention (the prompt-boundary rule matches herdr method strings in one adapter and cannot tell which module calls the `Agents` port), as for compaction today.

## Standards

How the design meets the engineering standards (DDD, SOLID, DRY):

- **DDD.** The ubiquitous language is `CONTEXT.md`; the new nouns (Handoff, Handoff source, Handoff target, Handoff plan, Handoff outcome, Handoff request, Lane claim, Freshness, Newer prompts, Worksite snapshot) are added there before code. Aggregates, each with one port and one repository: the request queue (`HandoffRequester`/`HandoffResponder` → `RequestsRepository`), the handoff answers (`HandoffAnswers` → its repository), the ledger (`Ledger`, read only here). The lane claims are a concrete in-process class (`LaneClaims`), not an aggregate. New value objects and brands: `HandoffId`, `HandoffRequest`, `HandoffAnswer`, `ClaimKind`, `Freshness`, `RefreshStatus`, `WorksiteSnapshot`, `ByteBudget`. Outcomes are discriminated unions with closed reasons. The domain stays pure (`recap-domain-pure`); parsing happens once at the edges (the CLI parses flags, the adapters parse herdr and git text); the composition roots are the daemon and the CLI, and nothing else wires adapters.
- **SOLID.** Single responsibility: the content builder, the vetting, the markdown serializer, the freshness computation, the worksite composition, the source resolver, the target resolver, the claim set and the delivery sender are separate small modules (the flow, the sender with the lease wrapper compaction already has, and the confirmation are three). Open/closed: a new agent kind adds one handoff plan to the adapter registry and the core never branches on a kind; a new source (the closed lane) is a new resolver behind `SourceResolver`; a new delivery mode or serialization is a new member of a closed list plus one registry entry. Liskov: every adapter honours its port's contract and the suites prove it: the handoff row of `test/adapter-conformance.test.ts`, a shared `Requests` contract test run against the SQLite repository and a new in-memory fake (none exists today), and a `WorksiteReader` contract test run against the git adapter and its fake. Interface segregation: `HandoffRequester`, `HandoffResponder` and `HandoffAnswers` instead of one wide `Requests`; `WorksiteReader` has only the two reads it needs. Dependency inversion: domain and application depend on ports; adapters depend inward; the ast-grep boundary rules (`recap-domain-pure`, `recap-layers-no-io`, `recap-transport-boundary`, `recap-prompt-boundary`, `recap-sqlite-readonly`, `recap-write-transactions`) enforce it and new probes make them bite on the new modules.
- **DRY.** One source of truth per concept: the outcome table (outcome, reason, storable, exit code, message key) is one typed table in the domain from which the union types, the exit mapping and the catalog-key check derive; the limits live in one application module; the forbidden words are one word list extracted from the compaction brief's `FORBIDDEN`, `PHRASES` and `WORDS` regexes, which are derived from it, imported by both flows; the idle/done ready set, the 400-code-point prefix and the CLI wait numbers are named constants; `CLOSED_SHOWN_MS`, the git timeout, `RECAP_WAIT_MS`, the typing-lease code, `requestNoteOf` and the in-flight function are imported, never copied; the one serializer is the only serializer of its format. The whitespace collapse shared by `plainText`, `requestNoteOf` and the serializer is one function with an explicit policy for control characters (`remove` for the note and the handoff text, `space` for token notes), so compaction's behaviour and tests stay unchanged. Duplication found in the touched area (the two copies of `RECAP_WAIT_MS`, the private in-flight function) is removed by sharing, without inventing an abstraction for two similar lines.

## Verification design

Tests cover the pure content builder and its pruning, stable ordering and identical output for identical inputs, vetting including the decision-with-forbidden-reason case, the serializer (no forged heading, first character), claim collisions in both directions, lease arbitration with `acquire(pane, 0)`, each adapter's conformance row, confirmation (baseline, prefix, fresh lane whose session appears after the send, a second handoff to the same target), the flow order (a refused target starts no refresh), the queue (age bound, withdrawal then re-read), CLI parsing and exit mapping, en/es parity, the prompt-boundary rule, and `--print` on a database not yet upgraded. Migration tests cover a fresh install and an upgrade ending at the latest version with the same schema, the CHECKs, and one answer per `HandoffId`. Daemon-flow tests use fake herdr wires and fake transcript, status and in-flight readers. The real-herdr delivery proof is an implementation task. The full plugin gates run after each task group, one at a time.

## Alternatives considered

- **Model-written brief:** rejected for slice 1: variance, cost, and crashed lanes may have no recent turns.
- **Current pane or tab id as source:** rejected: an explicit `--from` avoids a guess when a tab holds several tasks.
- **Tab-wide ledger:** rejected: facts of independent tasks must not be combined.
- **Plugin-created target pane:** rejected: pane lifecycle is not the plugin's responsibility.
- **Queue until the target becomes idle:** rejected: a later, unobserved state change could type into an unexpected lane.
- **In-process CLI flow with persisted claims:** rejected: a persisted lane-claim aggregate the daemon must read, while the daemon already owns the claims, the in-flight readers and the typing entry point.
- **A flat typed-line serialization and line delivery mode:** dropped from slice 1: no registered kind needs it (open question 4).
- **Freezing the handoff at close time (`handoff --snapshot`):** rejected: a crash gives no chance to run it; closed-lane retention is the later change.

## Decisions taken by the operator

- `--from` and `--to` accept pane identifiers only; a label is never resolved (decided 2026-10-10).
- Recently closed facts use the existing two-hour ledger window (decided 2026-10-10).
- Delivery is confirmed by the target's status becoming `working` OR by transcript evidence of the submitted text, as the adapter's plan declares (decided 2026-10-10).
- The handoff flow runs in the daemon from a `handoff` request-queue row, and the CLI waits for a typed answer (decided 2026-10-10).
- Vetting drops an offending fact and refuses `content-empty` only when nothing remains; the vocabulary is compaction's, without `tool` (decided 2026-10-10).
- Fact times and reasons, a bounded size with counted omissions, freshness and a forced refresh, a worksite snapshot, a verify-first preamble, a dry run and the locality rule were requested by the operator. How each is specified (the numbers, the Freshness fields, the 2 KiB worksite cap, the waits) is the author's recommendation; the budget numbers are open question 9.

## Decisions taken in review (2026-10-10)

- Asks are recorded in the token protocol's ask ledger (change `token-protocol`, migration 015), so this change builds no second ask store; this migration is 016.
- A restart answers every unanswered handoff ask `failed{interrupted}` (new storable reason), aligned with compaction; nothing is replayed.
- Storable reasons are validated by a code registry (the outcome table), not by a SQL literal list; adding a reason needs no migration.
- The settle time is a field of each kind's handoff plan: Claude 10 000 ms (measured 2026-10-10), Codex and OpenCode 10 000 ms unmeasured until the real-herdr task.
- The settle measurement of this change (group 8) is the canonical one for these agent kinds; its result, and the Claude
  figure above, are committed as metrics under `experiments/` at the repository root, and other tools cite that record.
- `HandoffOutcome` is a closed outcome table, not a fallible-operation result, so it stays its own sum; fallible reads
  (resolvers, refresh, repositories) return the repository's one `Result` from the token protocol module. `RefreshStatus` is
  a four-way status, named so it is not read as a result.
- The in-flight lookup stays behind an `InFlight` port so the application imports no adapter.
- Hermes declares `unsupported{no-plan}` through the `Capability` type.
- The `failed-lane-busy` compaction stage is declared in the `lane-tokens` capability, on top of the token protocol's text.
- The vocabulary stays compaction's without `tool` (the operator's decision); words about other tools are never written in this public repository, so they need no vetting.

## Open questions for the operator

Each has a recommended default, which the specification follows, and an alternative.

1. **Compaction on a handoff-held lane:** answer `failed-lane-busy` at once (default) or defer the compaction (alternative, not implementable while taken requests are deleted).
2. **Claude delivery:** the markdown as one first prompt through `agent.prompt` (default; if Claude shows a long paste unsubmitted the outcome is `failed{unconfirmed}`) or a flat text typed as one line with Enter (alternative; brings back a line mode, a second serializer and the typed-line rename).
3. **Done target:** a `done` status is ready, as `idle` is (default, matching compaction) or only `idle` is ready (alternative).
4. **Print without a target:** `--print` needs only `--from` (default) or also `--to` (alternative).
5. **Fresh lane without a transcript:** an `idle` or `done` lane whose transcript does not exist yet is ready (default), or it is refused until its first turn exists (alternative).
6. **Retained source:** a source lane that has closed is refused `source-unavailable` in slice 1 (default); the retention change adds it (alternative: in slice 1).
7. **Budget numbers:** 16 384 bytes and the newest 15 done, links and closed facts (default) or a smaller inline budget with a pointer to a file under the state directory beyond it (alternative; the receiver must be able to read the path).
8. **Worksite values and vetting:** paths, branch names, commit subjects and token names are exempt from vetting (default) or are vetted like facts (alternative; a repository whose name contains a forbidden word would lose its worksite lines).
9. **Transcript ownership for Codex and OpenCode:** a transcript shared by directory is not trusted; the status and the `awaiting` token decide (default) or such targets are refused until their own transcript exists (alternative).
