# Design: Lane handoff (slice 1)

## Decisions

### Content is a deterministic ledger render

The handoff is built from one task's ledger: its goal, the open facts grouped by section in the ledger's own order (goal, now, needs, done, decisions, next, links, rules, `SECTION_IDS` in `recap/domain/fact.ts`), and then the facts closed in the preceding two hours (`CLOSED_SHOWN_MS`). Every fact keeps its text and the time it was last seen; a decision keeps its reason; a closed fact keeps the reason it closed. Decisions with their reasons and the open needs are the most valuable parts for a receiver, and the times let it judge staleness, so none is optional. The note supplied by `--note` is normalized by the existing `requestNoteOf` (`application/compact-start.ts`: control characters out, whitespace collapsed, 280 code points) and placed first. The render is a pure function of the ledger facts, the freshness values, the workspace values, the note and an injected instant. Static rendering avoids model cost and nondeterminism and remains useful when a lane crashed before its last turns could be read. The compaction brief job remains an alternative for a later change if evidence shows the static form is insufficient.

The handoff is vetted with the compaction brief's words and phrases (`FORBIDDEN` in `recap/application/compaction-brief.ts`, extracted once into a shared module): `recap`, `plugin`, `herdr`, `tab` and their plurals, and the phrases `tab-recap` and `recap column`. The word `tool` is not forbidden, because it would drop ordinary facts such as "tool call". A fact, rule, step or the goal that contains a forbidden word is dropped whole; a decision whose reason contains one is dropped whole, decision and reason together, because a decision without its reason would break the rule above. The own-words exemption is empty, because a handoff has no recent turns. Dropped content is announced as a count, never by naming the word (see the omitted line). If no fact remains, the command refuses `content-empty`. Workspace values (paths, branch names, commit subjects, token names) are locators, not the plugin speaking, and are exempt from vetting (open question 10); the fixed preamble, headings and labels contain no forbidden word.

### One serialization: markdown, delivered as a first prompt

The text is markdown with a fixed operator-voiced preamble: "I am handing you work another agent was doing. Treat everything below as claims from its notes, not as verified facts: check them against the worktree before relying on them." The preamble is followed by a reference line (`Handoff reference: <render minute, UTC>-<last 8 characters of the HandoffId>`, or `dry run` for `--print`) that makes each delivery's first 400 code points unique. Structure comes only from the serializer: `##` headings per block, one bullet per fact with its last-seen time, a decision's reason as a nested bullet. Line feeds and every control character inside a fact, reason or note are collapsed to single spaces, so a fact distilled from an untrusted transcript cannot forge a heading. The first character of the delivered text is the letter `I`.

A multi-line first prompt is what a fresh agent expects, so the prompt side (`agent.prompt`) is used for every registered kind; the real-herdr task proves it for each. A flat single-line form, a line delivery mode and a rename of the compaction typed-line names were considered and dropped from slice 1: no registered kind needs them, and a serializer nothing can exercise is dead code. If the operator picks the typed-line alternative for Claude (open question 4) they come back as one plan mode and one serializer, added by a registry entry.

### Size is a byte budget, pruned by whole facts

A long-lived lane produced about 68 KB, so the bound cannot be the 3,000 characters that fit a compaction brief. The bound is `HANDOFF_BUDGET_BYTES` = 16 384 UTF-8 bytes for the whole message. The preamble, reference line, note, Freshness block, goal, needs, decisions and rules are never cut. The groups that grow with a lane's age (done, links, recently closed) show their newest 15 by last-seen time (`HANDOFF_DONE_SHOWN`, `HANDOFF_LINKS_SHOWN`, `HANDOFF_CLOSED_SHOWN`); if the text still exceeds the budget the oldest `now` and `next` facts are dropped whole. Every omission is counted in one visible line, `N facts omitted (done D, links L, closed C, now W, next X, withheld V)`, where `withheld` counts facts the vetting dropped, so the receiver knows the picture is partial without being told what was withheld. If the never-cut parts alone exceed the budget the command refuses `too-large`. The constants live in one application module (`application/handoff-limits.ts`) that imports `CLOSED_SHOWN_MS`; they are recommendations (open question 9). The writer-view pruning of the unmerged ledger-pruning change is not reused because it is not on main.

### Freshness, and the option to refresh

The ledger is written by the recap writer after turns; a lane started an hour ago may have no ledger yet, and a working lane has turns the ledger has not seen. Before the ledger the text states: when the ledger was last written and by which run cause (a new read, `lastRunOf(tab)`: `TabRecap` carries the time, `run.cause` the cause); the source lane's status; the newer user prompts, and the refresh result.

The newer user prompts are counted by reading the lane's transcript from the recap's cursor through the lane's reader (the cursor applies only while the stored transcript equals the located source, as in `recap-job.ts`). The reader reports no exhaustion and may skip the oldest part when the unread span exceeds its budget, so the count is a lower bound by construction: the line says `none` when the read reports no growth, `at least N` when it found N, and `unknown` when the transcript cannot be read. The metric is named "newer prompts", not "turns": CONTEXT.md defines a Turn as a status stretch.

A lane that has never had a recap run is refused `ledger-empty`. `--refresh` asks the daemon for a forced recap run first, waiting at most `HANDOFF_REFRESH_MS`; the compaction flow's `RECAP_WAIT_MS` (90 000, defined twice today in `daemon/compaction.ts` and `daemon/autocompact.ts`) is exported once from a shared module and both flows import it. Today `deps.refresh` returns void, so the flow cannot tell success from failure; the task adds a typed `RefreshResult` (`refreshed | failed | timed-out`) from the bounded wait and the tab's stored error. A failed or late refresh is stated in the block and does not stop the handoff. Without the flag the command never starts a run. `--refresh` with `--print` is a usage error. Only the target must be idle: a working source is legitimate.

### Workspace snapshot

A replacement agent also needs where the work is. After the ledger the text carries: the lane's directory as the store holds it; the repository root and branch (`LaneRepo`); the short hash and subject of the last commit; the count and the first 20, in git order, of the uncommitted paths; the five files the lane edited most (`countEdits`, `recap/application/edit-counts.ts`, the count `session-facts` shows with `FILES_SHOWN`); and the names, never the values, of the lane's herdr tokens that `awaiting` (`^awaiting(?:-.+)?$`, `domain/coordination.ts`) or the note rule of the same module (`note`, `note-<tool>`) match. A worktree path is not included: `LaneRepo` returns the top level only and `git rev-parse --git-common-dir` is not worth a third git call.

Git is asked through a new read-only `WorkspaceReader` port beside `LaneRepo`: no optional locks (`gitEnv()` already sets `GIT_OPTIONAL_LOCKS=0`), `core.fsmonitor=false`, and the 1 500 ms timeout (`TIMEOUT_MS`, exported once from the git adapter rather than imported from the git-note extension). The uncommitted paths need `git status --porcelain=v2 -z` records (renames carry a second path, untracked entries start with `?`, quoting is off with `-z`). `parseStatus` in the git note only counts lines, and no Node built-in parses porcelain v2, so a small hand-written parser is kept, tested on renames, untracked and unmerged entries. The last commit is `git log -1 --format=%h%x00%s`. Unknown values are omitted, a vanished directory yields the single line `workspace unavailable`, and the section is capped at 2 048 bytes, shrinking in this order: token names, edited files, uncommitted paths (dropped from the end), then the commit subject cut at a code-point boundary.

### Print is a dry run in the command's own process

`--print` renders exactly what would be delivered for file-transcript kinds (the CLI's transcript registry, `modalTranscriptRegistry()`, has no screen fallback, so a lane read from its screen gets `newer prompts: unknown`). Its inputs need no daemon: the ledger and the lane rows from the read-only store (the pane's tab comes from the `lane` rows the daemon published), the cursor and transcript through the registry, git through the `WorkspaceReader`, and herdr only for the target's status and the lane's token names, both omitted when herdr is unreachable. In-flight work, claims and the lease are not evaluated: they are the daemon's decisions, and with `--to` the target's status is shown on stderr as information. The read-only open reuses `connectReadOnly` (`adapters/db/connection.ts`) with its `{ readOnly: true }` literal and builds only the repositories `--print` needs (ledger, records, views); the store-wide opener prepares every repository's statements eagerly and would fail on a database not yet upgraded to the handoff tables. The command never writes a file: the operator keeps a dry run by shell redirection.

### Locality and consent

The command makes no network request, writes nothing outside the plugin's state directory except the delivery, and never writes a handoff body to a log (the daemon logs the request id, the outcome, the byte count, the omitted count and the withheld count). A ledger can hold anything the lane saw, so the README states that the operator is choosing to send it.

### Source selection

`--from <pane>` is required. The CLI finds the pane's tab in the `lane` rows of the read-only store; a pane with no row is refused `source-unavailable` before anything is queued. The daemon re-verifies, from its board, that the pane is a lane of that tab. The pane must belong to exactly one task in the tab's ledger (`readRecap(tab).tasks[].lanes`; the grouping gives a pane one task per run, so `task-ambiguous` is a defensive row). Other tasks' facts are never mixed in, and `tasks[0]` is never a fallback. `--from` accepts a pane identifier only.

The source is resolved through a typed seam, `SourceResolver`, answering `found{task}`, `source-unavailable`, `task-ambiguous` or `unknown`. Slice 1 implements it for a live lane; a later change adds a resolver for a retained closed lane without touching the content builder or the delivery. A source lane that holds a compaction claim or a handoff claim is refused `lane-busy`.

### Target selection and idleness

`--to <pane>` is required for delivery and names an existing pane. The operator creates a fresh agent with their normal workflow. The plugin never creates, closes, resizes, moves, swaps, focuses or otherwise changes a pane; starting an agent through plugin code was considered and rejected because it gives the plugin pane lifecycle responsibility.

The target is deliverable when its status is `idle` or `done`, nothing is in flight, and it carries no `awaiting` token. The in-flight reader (`inFlightOf` and the awaiting check, private to `daemon/autocompact.ts` today) is extracted into one application function shared by autocompact and handoff. It distinguishes a transcript that does not exist yet (`locate` answers `not-found`: a fresh lane, nothing can be in flight) from one that cannot be read (`unreadable`: refused `in-flight`). A pane the daemon has not discovered is refused `not-a-lane`. The queue holds a handoff only until the daemon takes it; a delivery never waits in the queue for a lane to become idle.

### The daemon flow, in order

1. Refuse `source-equals-target` before resolving either lane.
2. Resolve the source (task) and the target (lane, plan, status, in-flight): the cheap refusals come first, so a refused target starts no refresh.
3. If `--refresh` was given, run the bounded refresh.
4. Render: freshness, vetting, workspace, budget (`ledger-empty`, `content-empty`, `too-large`).
5. Take the lane claims with `claimAll([source, target])` (`lane-busy`).
6. Re-check the target's status and in-flight state, which a long refresh may have changed (`status-not-ready`, `in-flight`).
7. Take the typing lease with `acquire(pane, 0)`: no waiting; busy is `typing-lease-busy`, `unavailable` proceeds without a lease. The 60 s retry loop of the default `acquire` is not used.
8. Read the target's latest prompt as a baseline, send the prompt, confirm (below).
9. Release the lease and the claims on every path.

### Typed delivery per registered adapter

The handoff plan is a typed value owned by each registered kind's adapter, next to its compaction plan: its delivery mode (a closed union with one member, `prompt`), its confirmation evidence (`transcript`, `status`, or either) and no automatic retry. The sender executes the plan without branching on a kind. There is no prompt wait and so no stalled prompt: `HerdrAgents.prompt` throws `agent_prompt_stalled` only when a wait is passed, and the plan passes none. A kind without a plan is `unsupported{no-plan}`. `agent.prompt` is the only call, so `adapters/herdr-agents.ts`, the one module allowed to name it, needs a new method only if the existing `prompt` does not fit; it fits.

Confirmation reads at most `HANDOFF_OBSERVATIONS` (20) times, `HANDOFF_OBSERVE_MS` (1 000) apart; these equal the polling compaction plan's numbers, but they are separate constants because the two flows may diverge, and the conformance row pins both. On every observation the sender re-locates the target's transcript and re-reads its session from herdr, because a fresh lane has no transcript file until the first prompt is processed. Transcript evidence is `Transcripts.latestPrompt(source, budget)` with a tail budget of `HANDOFF_PROMPT_TAIL_BYTES` (65 536; a 16 KiB prompt is one JSON-escaped line and can exceed 16 KiB): the baseline taken before sending must differ from the new latest prompt AND the first 400 code points of the handoff, whitespace collapsed, must be a prefix of the collapsed new prompt. The baseline and the reference line make a delivery distinguishable from an earlier handoff to the same target. Status evidence is `Agents.status` reporting `working`; status-only confirmation is an accepted risk (other work also makes a lane work). All three kinds declare `either`. A send error is `failed{transport}`; a target reporting `blocked` when the prompt is sent is `refused{status-not-ready}`; an unconfirmed send is `failed{unconfirmed}`. No retry is automatic, because a retry could duplicate an instruction already accepted.

Delivery is entered only from a `handoff` request row that the daemon took from the request queue. The only writer of that row in this change is the operator's command; a later change that adds another writer amends this sentence and the prompt-boundary rule explicitly. The entry points of the prompt-boundary rule become two named operator paths: the compaction flow reached from the compaction request queue, and the handoff flow reached from the handoff request queue, both only because the operator asked. The `recap-prompt-boundary` and `recap-never-types` rules, their probes and their red-line rows are updated to name both paths.

### Execution, request queue and outcome record

The handoff flow runs in the daemon: the claims, the in-flight and awaiting readers and the typed-delivery wiring exist only there. The command performs its pre-queue checks, writes one `handoff` request row and waits for that request's answer. The daemon takes handoff rows in its request poll (`REQUEST_POLL_MS`, 1 s), runs the flow, and writes one answer row. The CLI maps the answer to an exit code.

`HandoffId` is the request row's UUIDv7 id, returned by the insert, so the CLI can poll and withdraw by it. The wait is at most 60 s, 150 s with `--refresh` (`HANDOFF_REFRESH_MS` plus the flow, about 22 s), read every 500 ms. Before queueing, the CLI checks that the daemon is running with `Pidfile.alive()` (the check `bin/tab-recap.ts` uses for `status`, `stop` and `launch`; `compact` does not perform it), and that the source pane's tab resolves; otherwise it refuses and writes nothing.

A taken request is never replayed: if the daemon restarts after taking one and before answering, nothing appears and the CLI reports `not-answered`. A row left in the queue (the CLI was killed before its withdrawal, or the daemon started late) is not delivered later: the daemon answers `failed{expired}` to any row older than `HANDOFF_ROW_MAX_AGE_MS` (180 s, the longest CLI wait plus a margin) without running the flow. On timeout the CLI withdraws its untaken request by id and reads the answer once more; when the withdrawal removed a row it reports `not-answered` with the withdrawn message (nothing was typed), otherwise, if still no answer, `not-answered` with the may-still-deliver message.

The next free migration number at implementation time (not hard-coded here: another open change plans migration 14 too) makes these changes in one rebuild, as migration 12 did, because a CHECK cannot be altered:
- `request` is rebuilt. Its `kind` CHECK gains `handoff`. New columns: `to_pane` (nullable, the target pane; `pane` holds the source pane) and `refresh` (`INTEGER NOT NULL DEFAULT 0`, 0 or 1). CHECKs: `kind <> 'handoff' OR (pane IS NOT NULL AND to_pane IS NOT NULL AND answer IS NULL)`; `kind = 'handoff' OR (to_pane IS NULL AND refresh = 0)`; the old rule for `compact` rows is kept (`kind IN ('compact','handoff') OR (pane IS NULL AND note IS NULL AND answer IS NULL)`). `request.target` holds the source pane's tab id. `request_readable` is recreated with the new columns.
- `handoff_answer` holds one row per accepted handoff keyed by `HandoffId`: `at`, `outcome` (`delivered`, `refused`, `unsupported` or `failed`) and `reason`, NULL exactly when `outcome` is `delivered`, restricted by CHECK to the storable reasons. Old answers are removed in the same `writeTx` as a new answer, after `HANDOFF_ANSWER_TTL_MS` (one hour; a separate constant from the token answer's `ANSWER_TTL_MS`, whose meaning is different). It has no foreign key to `request`, whose rows are deleted when taken.

The request queue and its answers stay one aggregate behind one repository (`RequestsRepository`), but the port is split by role: `HandoffRequester` (`requestHandoff`, `withdrawHandoff`, `handoffAnswer`), held by the CLI, and `HandoffResponder` (`takeHandoffs`, `answerHandoff`), held by the daemon; `Requests` extends both. `answerHandoff` runs in `writeTx`; the others are single statements like their siblings. `handoffAnswer` reads and never deletes, so a later change can read the same row.

The application returns a closed outcome union: `delivered`, `printed`, `refused{reason}`, `unsupported{reason}`, `failed{reason}`. `printed` exists only on the print path and is never stored. The reasons, their storability, exit codes and message keys are one table in the domain (see the lane-handoff spec); the CLI's exit mapping and the catalog-key test derive from it. Exit 0 is delivered or printed, 1 is refused, unsupported or failed, 2 is a usage error. Diagnostics go to stderr and carry no secret or handoff payload, except what `--print` writes to stdout.

### Lane claims

Compaction and handoff share one claim table in the daemon, renamed `LaneClaims` (from `CompactionClaims`). A claim has a kind (`ClaimKind`: `compaction | handoff`). `claim(pane, kind)` takes one pane. `claimAll(claims)` takes every pane of a handoff or none, in one synchronous step with no await between the check and the claim. Only a compaction claim has joined requests.

A compaction request for a pane that holds a handoff claim is not joined: it is answered `failed-lane-busy`, a new answer stage owned by `recap/domain/compact-request.ts` (`refusalAnswerOf('lane busy')`), recorded as a refused compaction with stage `failed` and why `lane busy`, and shown with the usual refusal toast. A compaction request for a pane that holds a compaction claim still joins. Autocompact is not affected: `busyOf` already reads `claims.has(pane)`, so an automatic request for a claimed lane is skipped with gate `busy` before any request is queued. A handoff's `lane-busy` refusal writes no compaction record and no decision.

Rejected alternatives: deferring the compaction until the handoff ends (a taken request row is deleted, so nothing can hold it for later), and joining the compaction to the handoff (the request would be dropped silently).

### Built-ins and hand-written pieces

The CLI uses `node:util` `parseArgs`. The UTC time `YYYY-MM-DD HH:MMZ` is `toISOString().slice(0, 16)` with the `T` replaced; the byte count is `Buffer.byteLength`; the note normalization is the existing `requestNoteOf`. Hand-written, with the reason no built-in fits: the ledger render and its pruning (no built-in knows the sections, the voice, the veto vocabulary or the budget rules); the markdown serializer (no built-in produces this fixed structure; it is a template over typed blocks, not a general markdown writer); the porcelain-v2 `-z` parser (no built-in parses it, and the git note's `parseStatus` only counts). English and Spanish command messages are typed i18n keys. No runtime dependency is added.

## Standards

How the design meets the engineering standards (DDD, SOLID, DRY):

- **DDD.** The ubiquitous language is `CONTEXT.md`; the new nouns (Handoff, Handoff source, Handoff target, Handoff plan, Handoff outcome, Handoff request, Lane claim, Freshness, Newer prompts, Workspace snapshot) are added there before code. Aggregates, each with one port and one repository: the request queue and its handoff answers (`Requests` → `RequestsRepository`, split by role), the ledger (`Ledger`, read only here), the in-process lane claims (`LaneClaims`). New value objects and brands: `HandoffId`, `HandoffRequest`, `HandoffAnswer`, `ClaimKind`, `Freshness`, `RefreshResult`, `WorkspaceSnapshot`, `ByteBudget`. Outcomes are discriminated unions with closed reasons. The domain stays pure (`recap-domain-pure`); parsing happens once at the edges (the CLI parses flags, the adapters parse herdr and git text); the composition roots are the daemon and the CLI, and nothing else wires adapters.
- **SOLID.** Single responsibility: the content builder, the vetting, the markdown serializer, the freshness computation, the workspace composition, the source resolver, the target resolver, the claim set and the delivery sender are separate small modules. Open/closed: a new agent kind adds one handoff plan to the adapter registry and the core never branches on a kind; a new source (the closed lane) is a new resolver behind `SourceResolver`; a new delivery mode or serialization is a new member of a closed list plus one registry entry. Liskov: every adapter honours its port's contract and the suites prove it: the handoff row of `test/adapter-conformance.test.ts`, a shared `Requests` contract test run against the SQLite repository and a new in-memory fake (none exists today), and a `WorkspaceReader` contract test run against the git adapter and its fake. Interface segregation: `HandoffRequester` and `HandoffResponder` instead of one wide `Requests`; `WorkspaceReader` has only the two reads it needs. Dependency inversion: domain and application depend on ports; adapters depend inward; the ast-grep boundary rules (`recap-domain-pure`, `recap-layers-no-io`, `recap-transport-boundary`, `recap-prompt-boundary`, `recap-sqlite-readonly`, `recap-write-transactions`) enforce it and new probes make them bite on the new modules.
- **DRY.** One source of truth per concept: the outcome table (outcome, reason, storable, exit code, message key) is one typed table in the domain from which the union types, the exit mapping and the catalog-key check derive; the limits live in one application module; the forbidden words are the compaction brief's `FORBIDDEN` set extracted once and imported by both flows; `CLOSED_SHOWN_MS`, the git timeout, `RECAP_WAIT_MS`, the typing-lease code, `requestNoteOf` and the in-flight function are imported, never copied; the one serializer is the only serializer of its format. Duplication found in the touched area (the two copies of `RECAP_WAIT_MS`, the private in-flight function) is removed by sharing, without inventing an abstraction for two similar lines.

## Verification design

Tests cover the pure content builder and its pruning, stable ordering and identical output for identical inputs, vetting including the decision-with-forbidden-reason case, the serializer (no forged heading, first character), claim collisions in both directions, lease arbitration with `acquire(pane, 0)`, each adapter's conformance row, confirmation (baseline, prefix, fresh lane whose session appears after the send, a second handoff to the same target), the flow order (a refused target starts no refresh), the queue (age bound, withdrawal then re-read), CLI parsing and exit mapping, en/es parity, the prompt-boundary rule, and `--print` on a database not yet upgraded. Migration tests cover a fresh install and an upgrade ending at the latest version with the same schema, the CHECKs, and one answer per `HandoffId`. Daemon-flow tests use fake herdr wires and fake transcript, status and in-flight readers. The real-herdr delivery proof is an implementation task. The full plugin gates run after each task group, one at a time.

## Alternatives considered

- **Model-written brief:** rejected for slice 1: variance, cost, and crashed lanes may have no recent turns.
- **Current pane or tab id as source:** rejected: an explicit `--from` avoids a guess when a tab holds several tasks.
- **Tab-wide ledger:** rejected: facts of independent tasks must not be combined.
- **Plugin-created target pane:** rejected: pane lifecycle is not the plugin's responsibility.
- **Queue until the target becomes idle:** rejected: a later, unobserved state change could type into an unexpected lane.
- **In-process CLI flow with persisted claims:** rejected: a persisted lane-claim aggregate the daemon must read, while the daemon already owns the claims, the in-flight readers and the typing entry point.
- **A flat typed-line serialization and line delivery mode:** dropped from slice 1: no registered kind needs it (open question 4).
- **Freezing the handoff at close time (`handoff --snapshot`):** rejected: a crash gives no chance to run it; closed-lane retention is the later change.

## Decisions taken by the operator

- `--from` and `--to` accept pane identifiers only; a label is never resolved (decided 2026-10-10).
- Recently closed facts use the existing two-hour ledger window (decided 2026-10-10).
- Delivery is confirmed by the target's status becoming `working` OR by transcript evidence of the submitted text, as the adapter's plan declares (decided 2026-10-10).
- The handoff flow runs in the daemon from a `handoff` request-queue row, and the CLI waits for a typed answer (decided 2026-10-10).
- Vetting drops an offending fact and refuses `content-empty` only when nothing remains; the vocabulary is compaction's, without `tool` (decided 2026-10-10).
- The operator supplied field evidence (2026-10-10): fact times and reasons, a bounded size with counted omissions, freshness and a forced refresh, a workspace snapshot, a verify-first preamble, a dry run and the locality rule. How each is specified (the numbers, the Freshness fields, the 2 KiB workspace cap, the waits) is the author's recommendation; the budget numbers are open question 9.

## Open questions for the operator

Each has a recommended default, which the specification follows, and an alternative.

1. **Execution model:** the daemon runs the flow from a request-queue row (default) or the CLI runs it in process with persisted claims (alternative).
2. **Offending content:** drop the fact and deliver the rest (default) or refuse the whole handoff on any hit (alternative).
3. **Compaction on a handoff-held lane:** answer `failed-lane-busy` at once (default) or defer the compaction (alternative, not implementable while taken requests are deleted).
4. **Claude delivery:** the markdown as one first prompt through `agent.prompt` (default) or a flat text typed as one line with Enter (alternative; brings back a line mode, a second serializer and the typed-line rename).
5. **Done target:** a `done` status is ready, as `idle` is (default, matching compaction) or only `idle` is ready (alternative).
6. **Print without a target:** `--print` needs only `--from` (default) or also `--to` (alternative).
7. **Fresh lane without a transcript:** an `idle` or `done` lane whose transcript does not exist yet is ready (default), or it is refused until its first turn exists (alternative).
8. **Retained source:** a source lane that has closed is refused `source-unavailable` in slice 1 (default); the retention change adds it (alternative: in slice 1).
9. **Budget numbers:** 16 384 bytes and the newest 15 done, links and closed facts (default) or a smaller inline budget with a pointer to a file under the state directory beyond it (alternative; the receiver must be able to read the path).
10. **Workspace values and vetting:** paths, branch names, commit subjects and token names are exempt from vetting (default) or are vetted like facts (alternative; a repository whose name contains a forbidden word would lose its workspace lines).
