# Design

## Context

See proposal.md (Why). Many processes open the state at once: the daemon (the only regular writer),
one column process per agent tab (about 27 in practice), the CLI and the setup modal (which only queue
requests). The plugin runs straight from source with zero runtime dependencies.

## Goals / Non-Goals

**Goals:** one normalized store (every fact once, the rest derived); the store never accepts a shape the
renderer does not know; safe concurrent use by many processes; upgrades that can always be undone.

**Non-Goals:** a remote or shared database; history features (next change); down migrations.

## Decisions

1. **`node:sqlite`, no ORM or query builder.** Drizzle, Prisma or Kysely would add a runtime dependency.
   One repository per aggregate (recap records, tab views, column visibility, requests), each behind
   its own port; SQL lives only in `src/adapters/db/`; rows are decoded at the edge.
2. **Normalized schema (3NF).** Live state: `tab`, `lane`, `transcript`, `column_state`,
   `tab_visibility`, `request`, `store_meta`. History: `chapter`, `boundary`, `task`, `run`,
   `run_read`, `run_task`, `run_task_lane`, `item`. A recap's markdown, time, cost and language are
   derived from its last good run; `tab.backend`/`tab.error` hold the live writer and the last error
   line (state, not run facts). Every foreign-key column is indexed (a test walks them).
3. **Ids: UUIDv7 as `BLOB(16)` in `WITHOUT ROWID` tables**, generated by our own monotonic generator
   (Node's `crypto.randomUUIDv7` is newer than our floor and is not monotonic within a millisecond —
   measured: 10 007 of 20 000 out of order). Only the creation time lives in an id. Shown at the edges
   as `<prefix>_<26 Crockford base32>`; Node has no base32 encoder.
4. **Money as integer micro-USD.** Summing floats drifts.
5. **Concurrency:** WAL (set once at creation), `synchronous=FULL`, a 2 s busy timeout, and every write
   transaction is `BEGIN IMMEDIATE` through one helper (a lint rule rejects a bare `BEGIN` elsewhere);
   column processes never hold a read open between ticks; the daemon checkpoints the WAL every 10 min.
6. **Migrations:** `PRAGMA user_version`; foreign keys off before `BEGIN IMMEDIATE` (the pragma is a
   no-op inside a transaction), `foreign_key_check` before commit; backups with `VACUUM INTO`
   (synchronous; `sqlite.backup()` is async); released migration files are immutable (CI check).
7. **The file import is not a migration:** daemon-only, tracked in `store_meta`, one transaction with a
   read-back comparison through the new repositories before commit.

## Risks / Trade-offs

- [Rolling back to 1.5.1 after running 1.6.0 shows the state as it was at the upgrade] → documented;
  delete `tab-recap.db*` to import again after moving forward.
- [WAL on a network filesystem corrupts] → the state directory must be on a local disk (documented).
- [Old columns still running 1.5.1 read the moved files] → columns re-execute themselves on a version
  change, so they pick up the new code.

## Migration Plan

Release as 1.6.0. Before deploying, run the import dry-run against a copy of the live state directory.
Rollback: stop, move `legacy-files-*` back, check out 1.5.1, start.
